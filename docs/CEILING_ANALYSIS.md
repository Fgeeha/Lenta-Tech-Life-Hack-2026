# Ceiling-анализ — физические пределы задачи

## Методология

Ceiling-анализ измеряет максимально достижимую метрику **при идеальном детекторе**:
вместо детектированных bbox мы используем GT-bbox (из разметки), запускаем production OCR+QR и
считаем долю верных полей. Это позволяет разделить ошибки на два независимых источника:

1. **Ошибки детекции** (detection recall/precision) — не влияют на ceiling
2. **Ошибки OCR/QR** — это и есть ceiling

Результат: если ceiling = X, то никакое улучшение детектора не даст метрику выше X.

## Разбор каждого поля

### price_discount (0.972)
GT значение = «нет» в 100% строк. Наша модель предсказывает «нет» по умолчанию → почти
всегда верно. Это baseline, не реальный OCR-результат.

### price_card (0.420) + price4_qr (0.458)
Самое крупное число в оранжевой зоне ценника. OCR читает его в 42% случаев.
price4_qr выше (45.8%) потому что даже когда OCR не читает, деривация `price4_qr ← price_card`
захватывает дополнительные случаи. Основная причина провалов: слияние числовых токенов при
высоком upscale (`302345` вместо `3789` + `2345`). Решение: upscale=2 без CLAHE/sharpening.

### discount_amount (0.200)
Деривируется из двух цен: `int((1 - price_card / price_default) * 100)%`.
Работает когда обе цены прочитаны корректно. GT хранит скидку floor-округлением (не round).

### price_default (0.069) + price1_qr (0.082)
Меньший шрифт в оранжевой зоне. OCR читает реже. price1_qr чуть лучше за счёт деривации
от price_default.

### id_sku (0.048)
12-значный артикул (Lenta: `270207736530`). Мелкий шрифт в белой зоне ценника.
Иногда читается при удачном кадре, чаще нет.

### barcode + qr_code_barcode (0.019 каждый)
Успешно декодируется только через QR-path. Прямой pyzbar на штрихкод: **0/274** ни на одном
видео. QR-code успех: **2/274 (0.7%)**.

**Почему barcode = 0.019, а не 0.7%?**  
Потому что 0.019 × 274 ≈ 5 тегов. Часть из них — QR decoded (2) + случайные совпадения
регуляром на длинных цифровых строках.

### product_name (0.008)
Кириллический текст в мелком шрифте. Token-overlap Jaccard ≥ 0.40.
EasyOCR [ru, en] при 3x upscale возвращает нечитаемые результаты на 99%+ кропов из-за
комбинации: motion blur + стеклянная полка + низкое разрешение.

## Почему metric@80% = 0.004

Порог 80% = нужно ≥ 9 из 11 полей верными. Среднее число верных = 2.4.  
Разрыв 2.4 → 9 = требует улучшения в 3-4 независимых полях одновременно.

**Единственный сценарий достижения порога:**
- QR успешно декодирован → сразу +6 полей (barcode, qr_code_barcode, price1-4_qr)
- + price_card верный (OCR) → +1
- + price_discount = «нет» → +1
- + discount_amount деривация → +1
- Итого: 9/11 → PASS

Это произошло 1 раз из 274 (тег idx=10 в 26_12-20): вино с четко видимым QR.

## Что ограничивает QR-декодирование

```
Дистанция робот-полка: ~2-3 м
Фокусное расстояние камеры: ~28mm эквивалент
Физический размер QR на ценнике: ~25×25 мм
Пиксельный размер QR в 4K (3840×2160): ~20-30 px
```

pyzbar требует минимум ~20x20 px для QR. На грани, плюс motion blur и стекло.
qreader (deep-learning detector): 2/274.
WeChatQR: 0/274.
Full-frame qreader (не crop, весь 4K кадр): 0 дополнительных.

## Что ограничивает barcode-декодирование

```
Физический размер barcode на ценнике: ~40×15 мм
Пиксельный размер в 4K: ~35×13 px
Ширина одного модуля EAN-13: ~0.35 px в видео
```

Минимум для pyzbar: ~2 px/модуль. Реальность: 0.35 px/модуль = в 6 раз меньше минимума.  
Даже при 6x upscale на ROI: 2.1 px/модуль — на грани, но H.264-артефакты уничтожают полосы.

## Вывод

Ceiling = 0.004 при текущих данных не является ошибкой в алгоритме.  
Это физический предел разрешения видео для данного расстояния и камеры.  
Detection recall = 100%, field matching = корректен.  
Потолок поднимается только аппаратными или data-инженерными улучшениями,
описанными выше.
